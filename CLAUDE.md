# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Electron + Babylon.js desktop app that passively visualizes Claude Code / Codex agent sessions as a persistent universe: projects are solar systems (grouped into galaxies), live sessions are starships, subagents are drones, and verified file edits grow planets. The main process tails provider JSONL transcripts; it never owns or launches the observed agents (two narrow LIVE-only exceptions: opening the host terminal at a project, and starting Codex on a tagged `GOALS.md` item from the IDEAS queue). Windows and macOS are first-class; Linux runs the viewer but has no terminal control. See `docs/MACOS-LAUNCH.md` for the platform matrix.

## Commands

- `npm start` — run the app
- `npm run setup` — one-step install: dependencies if Electron is missing, the launcher shortcut for this OS, then opens the app. `Install Agent Orrery.cmd` / `.command` in the root run it
- `npm test` — all tests (Node's built-in runner)
- `node --test test/ship-assets.test.js` — single test file
- `node kit/grade.mjs` — mechanical renderer regression gate; run after ANY renderer change, must stay green. Runs against the synthetic profile in `scripts/lib/synthetic-profile.mjs` (`--real` uses your own transcripts and app state) and replaces only its own files in `.shots/`
- `npm run shots` — headless screenshot mode; writes `.shots/*.png` for visual comparison against the three mockup PNGs in the repo root (gold samples: `3.universe-map-view.png` → universe, `2.solar-system-view.png` → system, `1.planet-view.png` → planet)
- `npm run ships:generate` — regenerate procedural ship GLB assets
- `npm run typecheck` — type-checks the JSDoc in `src/` (`tsconfig.json`: main + preload; `src/renderer/tsconfig.json`: renderer; shared shapes in `src/types/`). Only files whose first line is `// @ts-check` are checked: every `src/` JS file except the older renderer code that predates it (the `scene-*.js` files, `util.js` and `util-scene.js`, `galaxy-layout.js`, `polish-math.js`), and every new file. Runs in CI; there is no lint tooling.

## Hard constraints (from kit/SPEC.md — read it before renderer work)

- **Frozen files** — change only when the owner asks: `assets/*`, the mockup PNGs, `src/preload.js` (the renderer's only bridge; see `kit/SPEC.md` §3), and `package.json` (no new dependencies or scripts without asking; `typescript` is a dev-only checker). `main.js` is a bootstrap; concerns live in `app-context.js`, `window.js`, `menu.js`, `replay-control.js`, `ipc/`, `harness/`.
- Security fixes stay minimal and carry a `// Security` comment at the edit site.
- Renderer is plain JS with classic `<script>` tags — **no ES modules** (file:// CORS), no `.ts` files (types are JSDoc checked by `npm run typecheck`), no bundler, no npm installs. Renderer code attaches to the single `window.AUR` namespace; script load order in `src/renderer/index.html` provides globals.
- Babylon loads from local UMD bundles in `node_modules` (`BABYLON`, `BABYLON.GUI` globals). Renderer is fully offline — zero network requests; the UI fonts ship locally under `src/renderer/fonts/` (OFL, declared in `styles/tokens.css`, generated from `design/tricolor/tokens.json`), and Babylon GUI labels keep the system font stack.
- `contextIsolation` is on; the renderer's only channel to the main process is the `window.AU` bridge defined in `src/preload.js` and documented in `kit/SPEC.md` §3.
- One `BABYLON.Engine` for the app lifetime; each view builds its own `BABYLON.Scene` and disposes it on view switch.
- Files stay at about 300 lines, 400 at most; going over needs a written reason. `grade-main-split.mjs` (src/main) and `grade-structure.mjs` (src/renderer) fail any file over 400.
- Never generate or download art ad hoc — use a procedural fallback in code and log the want in `kit/ASSET-REQUESTS.md`.

## Architecture

**Main process (`src/main/`)** — `main.js` is a bootstrap: it reads `flags.js`, builds the context in `app-context.js` (service construction and cleanup; the shared runtime objects such as `win`, `tracker`, `replaySource`, `activeSource` and `streamEpoch` are fields of `ctx`), attaches `replay-control.js` (live/replay source switching and playback commands) and the `ipc/` handler factories (`guards`, `terminal`, `tasks`, `root-tasks`, `project-paths`), registers the `au:*` table through `ipc/register.js`, and creates the window through `window.js`. No module under `src/main` has module-level state: shared state is a field of `ctx`, and state used by one concern is private to that concern's factory. `tracker.js` is the live façade over `live/`: one `LiveModel` (`live/model.js`) that the per-provider discovery (`claude-source`, `codex-source`, `signal-source`), the tails and record reducers (`claude-records`, `provider-records`), `projects`, `ships`, `builds`, `attention`, `events` and `system-view` modules act on; it tails Claude/Codex transcript JSONL (plus metadata-only "Signal" directories) and derives ships/planets/events. `replay-source.js` is the history façade over `history/`: `index-builder` (bounded file/time index), `record-reader` (per-source cursors), `merge` + `order` (time-ordered merge), `historical-line`, `apply-record`, `model`, and `checkpoints` + `checkpoint-plan` (in-memory seek checkpoints); it reconstructs the same event vocabulary for playback while the live Tracker keeps running. `universe/` holds what both share: galaxy grouping, the public project/ship shapes, procedural planets and the ship record. `terminal-launcher.js` / `agent-launcher.js` implement the two LIVE-only actions; `goals.js` + `root-tasks.js` + `root-task-coordinator.js` + `task-runs.js` back the global IDEAS queue; `project-vcs-status-*` + `github-metadata-provider.js` supply per-project git/GitHub status. `window-security.js` hardens web contents and validates trusted frames.

**Renderer (`src/renderer/`)** — three Babylon views registered as `AUR.views.<name>(engine, data, ctx) => { scene, update(eventBatch), dispose() }`: `scene-universe.js` (galaxy map) → `scene-system.js` (one project) → `scene-planet.js` (planet close-up), orchestrated by `app.js`. A view's parts live in `scene-<view>-*.js` files that register on `AUR.sceneParts.<view>` (created by `scene-common.js`) and load before the view; the view builds one explicit `view` object and merges its parts into it. `ship-assets.js` (+ `-hulls`, `-api`) publishes `AUR.ships`; `util-scene.js` holds the Babylon helpers that `util.js` used to. The app layer is split into `app-*.js` modules on the `AUR.app` namespace: `app-state.js` loads first and is the only file that assigns `AUR.app` (shared state in `AUR.app.state`, constants in `AUR.app.const`), each other module is one IIFE that throws if `AUR.app` is missing and publishes cross-module functions as `AUR.app.<fn>` without calling another module at load time, and `app.js` loads last and keeps boot, event routing, view switching and debug hooks. `util.js` copies `fnv1a`/`mulberry32` from `src/main/shared/hash.js` so seeds agree between processes (`test/shared-hash.test.js` checks they match). `galaxy-layout.js` and `polish-math.js` are pure UMD/Node-testable helpers — keep them dependency-free.

**Kit workflow (`kit/`)** — this repo is developed via "kits": self-contained contract + rubric + grading-script packages executed by agents (see the `/distill` skill and `kit-runner` agent). `kit/README.md` is the status board; `kit/SPEC.md` is the live renderer contract (update it when the app evolves); `kit/RUBRIC.md` is the visual acceptance reference; completed kits are archived under `kit/done/<name>/` with their own grade scripts, pending ones live in `kit/todo/`. Each done kit's gate (e.g. `node kit/done/attention/grade-attention.mjs`) must keep passing.

**Test-mode flags** — `flags.js` parses `--shots`, `--polish-test`, `--provider-test`, `--history-test`, `--control-test`, each with an `--<name>-output=` path; `main.js` dispatches to the matching runner in `harness/modes/` (with `harness/driver.js`, `harness/metrics.js` and `harness/fixtures.js`), driving fixture-based headless runs used by the grade scripts.

Additional docs live in `docs/` (design direction, roadmap, playback, multi-provider, agent control, Windows launch).
